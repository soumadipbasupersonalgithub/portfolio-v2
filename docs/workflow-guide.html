What actually happens, step by step

Numbered because it really is a sequence — each step gates the next.

  1. A pull request targets main

    The AI reviewers (Claude / Codex) read the diff independently. In parallel, the quality gate takes over the mechanical verification — nothing merges on vibes.

  2. Jenkins finds out

    A GitHub webhook (tunnelled with ngrok, since Jenkins runs on a home machine) pings Jenkins instantly. If the tunnel is down, a 5-minute repository scan catches the PR anyway — two triggers, zero missed builds.

  3. The PR branch is built and served

    npm ci && npm run build, then the built dist/ is served on localhost:4173. Tests never touch the live site — they exercise exactly the code the PR proposes.

  4. Playwright: functional

    105 tests across desktop (1920×1080), tablet (iPad Pro 11, WebKit) and mobile (Pixel 7): navigation, every link and image, section content, the contact form against a mocked Web3Forms API, and zero console errors allowed.

  5. Playwright: visual regression

    Eight sections × three viewports, screenshot-compared against committed baselines with a 2% pixel tolerance. Animated elements are frozen during capture, so a diff always means the UI really changed.

  6. Lighthouse

    Three audit runs against the served build; median scores must clear the thresholds in lighthouserc.cjs — performance ≥ 0.80, accessibility / best-practices / SEO ≥ 0.90.

  7. The verdict lands on the PR

    Jenkins posts the ci/jenkins/quality-gate commit status. Branch protection makes it required: green unlocks the merge button, red keeps it locked. An optional toggle (AUTO_CLOSE_ON_FAILURE) goes further and closes failed PRs with an explanatory comment.

The architecture, simplified

One pipeline, two runtimes. The Jenkinsfile detects at runtime where it's standing and picks the right lane — same stages, same thresholds either way.

Lane A · Linux + Docker

Containerized (preferred)

On a Linux node with Docker, everything runs inside the official Playwright image.

  • Browsers preinstalled, rendering deterministic
  • linux visual baselines gate the build
  • Lighthouse via lhci autorun
Lane B · direct on host

Host mode (this machine)

On Windows — where Docker can't mount workspaces into Linux containers — the gate runs directly on the node.

  • Browsers installed once, then cached
  • win32 visual baselines gate the build
  • Lighthouse run directly + scores asserted by scripts/assert-lighthouse.cjs

Everything the pipeline needs lives in the repo: Jenkinsfile (the stages), playwright.config.ts + tests/ (what green means), lighthouserc.cjs (how fast is fast enough), and docs/JENKINS_SETUP.md (how the server was stood up). Jenkins itself holds only two things: a GitHub token stored as a credential, and the job pointing at the repo.

Red vs green — what each outcome means

StatusWhat happenedWhat happens next
✓ success All 129 tests passed and Lighthouse cleared every threshold. Merge button unlocks. Ship it.
◐ unstable Tests passed but visual baselines didn't exist yet for this platform — the pipeline created them. PR check still passes. Download the baselines from the build artifacts and commit them to arm the visual gate.
✕ failure A test failed, a screenshot diverged beyond 2%, or a Lighthouse median dipped below threshold. Merge stays blocked. The Playwright and Lighthouse HTML reports on the build show exactly what broke. If AUTO_CLOSE_ON_FAILURE=true, Jenkins also comments and closes the PR (reopen after fixing).
